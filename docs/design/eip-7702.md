# EIP-7702 Delegated Accounts

EIP-7702 lets an EOA set a persistent delegation indicator that points to
contract code. Calls to the EOA then execute the delegated code in the EOA's
own account context, preserving the address and existing assets.

Loom supports this as an adoption path, not as an upgrade authority.

## Model

1. The user signs a 7702 authorization that delegates the EOA to reviewed Loom
   account runtime code.
2. The EOA sends a self-call to `initializeDelegatedAccount(...)` with the
   reviewed EntryPoint address for that chain.
3. Initialization installs the user's validators, hooks, recovery module,
   guardian root, and config hash into the EOA's storage.
4. After initialization, the EOA follows the same Loom validation, direct
   execution, scheduling, recovery, freeze, vault, and migration rules as a
   constructor-deployed Loom account.

`initializeDelegatedAccount` is callable only when `msg.sender == address(this)`
and `configVersion == 0`. It writes the selected EntryPoint into account storage.
A normal constructor-deployed or proxy-deployed Loom account has
`configVersion == 1`, so it cannot be reinitialized through the 7702 path.

The runtime carries a second initializer, `initialize`, which exists solely so
`LoomAccountProxy` can bootstrap itself from its own constructor. It cannot
require `msg.sender == address(this)`, because during proxy construction the
caller is the factory. It is instead restricted to that context: it reverts with
`InvalidInitializationContext` unless `address(this)` has no code and is not the
runtime's own deployment address. A proxy inside its constructor is the only
account that satisfies this; a delegated EOA always carries the 23-byte
`0xef0100 || template` delegation indicator as its code, so `initialize` can
never reach a delegated account.

This separation is load-bearing. Without it, an uninitialized delegated EOA has
`configVersion == 0` and `initialize` had no caller check, so any observer of the
delegation transaction could front-run the owner's self-initialization and
install an attacker-chosen EntryPoint, validator set, hooks, and guardian
configuration. Because `_initialize` writes `configVersion = 1`, the real owner's
`initializeDelegatedAccount` would then revert permanently and every recovery
path would key off the attacker's guardian root.

Delegated initialization needs no separate signature envelope. Requiring the EOA
itself to send the transaction means the EOA key authorizes the exact payload,
the EOA's own transaction nonce provides replay protection, and the
transaction's chain id provides chain separation. See
`docs/decisions/0015-initialization-context-separation.md`.

## Security posture

- 7702 delegation is persistent. A malicious authorization can hand execution
  of the EOA to hostile code. Loom clients must never ask users to delegate to
  unreviewed code.
- Initialization is deliberately separate from the authorization tuple because
  EIP-7702 does not run initcode. A delegated EOA that has not initialized has
  no installed validator and cannot execute Loom-controlled operations.
- The delegated runtime address and initializer EntryPoint are trust decisions.
  Users and clients must verify runtime source, runtime bytecode, compiler
  settings, EntryPoint bytecode, and deployment chain before signing and
  initializing.
- Loom does not add a registry, admin key, relayer, or recovery provider for
  7702 adoption.
- Chain-specific authorization should be preferred. Chain-agnostic 7702
  authorizations expand replay and phishing blast radius.

## Non-goals

- No automatic asset migration is needed; assets remain at the EOA address.
- No delegated-code upgrade mechanism is added. Future code changes require a
  new 7702 authorization by the EOA.
- No claim is made that 7702 is safer than a fresh Loom account. It is an
  adoption bridge for users who need address and asset continuity.
